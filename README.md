# Cricket Auction Application

A full-stack cricket auction management app: React (Vite) frontend, Node.js/Express backend, MySQL database.

## Features

0. **Admin login** — every page except `/login` requires an authenticated admin session. Enter username/password on the login page to receive a JWT (stored in `localStorage`), which is then attached as a `Bearer` token to every API request. A **Logout** button in the header clears the session and returns to the login page. Wrong username and wrong password show the same generic error so a caller can't tell which one was wrong.
1. **Auction Rooms** — create an auction room (name, date, number of teams, purse value, bid step-up value), start the auction, or delete a room.
2. **Manage Auction** (players & teams tabs):
   - **Players** — add players with name, category (Batsman / Bowler / All Rounder), base value (defaults to 1000), an optional **profile picture** upload (up to 3MB), and flags for Captain / Icon player. The photo replaces the initials avatar everywhere the player shows up (players table, roster modal, and the Live Auction page). Click **Edit** on any player to update these fields in a modal dialog, including replacing the profile picture. Click the **Player** column header to sort by name (ascending/descending). **Export to Excel** downloads the current list (respects the active sort) with a **Photo** column embedding each player's actual profile picture next to their row (client-side, via `exceljs`; whatever format the photo is stored in, the browser decodes it onto a canvas and re-encodes it as PNG before embedding, so it always renders correctly regardless of source format). **Import from Excel** bulk-adds players from an `.xlsx`/`.xls` file (columns: Player Name, Category, Base Value, Captain, Icon Player, Photo — invalid rows are skipped with a reason, valid ones are added); the Photo column accepts either an embedded image or a plain image URL/hyperlink — either way it's fetched, converted, and uploaded as the new player's profile picture, exactly as if it had been chosen via the picker. **Every profile picture is stored as WebP** on the server regardless of how it arrived (manual upload, an embedded Excel image, or a photo link) — the original format is discarded once converted. Add/remove/import and full editing are locked once the auction starts, but a **📷 Photo** button remains so a missing or wrong picture can still be fixed without disrupting the live auction; export stays available anytime. **🗑️ Delete All Players** (next to the Add Player heading, shown whenever there's at least one player) opens a confirmation dialog before permanently removing every player in the room, including their photos. It's only available before the auction starts, same as adding/removing individual players, and — even during that setup window — is refused if a tournament has already started for this room (the server re-checks both conditions itself, since the room could otherwise be mid-auction with players already sold and teams' purses already deducted).
   - **Teams** — add teams with team name, logo upload, and number of players. Each team gets its own purse (starting at the room's purse value). **📄 Download Auction Report**, next to the Teams heading, generates the same results PDF as Finish Auction (team-by-team roster, sold prices, jersey details) at any point — before, during, or after the auction — reading whatever's been bought so far; a team with nothing purchased yet just shows "No players purchased." instead of an error. Alongside it, **🏊 Pool Players** downloads a separate PDF listing every player not yet assigned to a team — photo (re-encoded from whatever format it's stored in, so it renders reliably regardless of source format), name, category, base value, and whether they're still Pending or were marked Unsold — this button is only available while the auction hasn't been marked completed yet, and disappears from the Teams section once it has (there's no more "pool" left to report on at that point). Click a team any time to open its **roster** and assign jersey number, size (XS–4XL) and sleeve type (Full/Half) to its purchased players — the header (title, close button, and column labels) stays put while a long roster scrolls underneath it, and hovering a row highlights it. The same roster modal also has:
     - **Team Owner** — a free-text name for who owns/manages the team, plus their own jersey number and size (XS–4XL), editable any time (purely informational, shown on the team's card).
     - **Generate Report** — a button at the bottom of the roster modal downloads a PDF jersey report for that team (client-side, via `jspdf`/`jspdf-autotable` like the auction-results PDF): the team's logo top-left (if uploaded), team name, the owner's name/jersey/size if set, and a table of every player's name, category, jersey number, size and sleeve type. Available as soon as the team has at least one player — jersey number, size and sleeve are entirely optional and just show as "-" per player when not yet entered, so the admin isn't blocked from generating the report while jersey assignment is still in progress.
     - **Captain** — lets an admin lock in a team's captain *before the auction starts*, at a base value they set directly rather than through bidding: the dropdown offers only players already flagged **Captain** in the Players tab (and not yet sold or assigned elsewhere) — pick one and enter a price, and **Assign** immediately sells that player to the team at that price (deducted from its purse) — since the auction's pool only ever looks at players still `pending`, this player is skipped entirely, never coming up for bidding. Each team can have one directly-assigned captain at a time; **Unassign** reverses it (refunds the purse, returns the player to the pending pool) so it can be redone. Both actions are blocked once the auction has started — captains have to be settled during setup. If no player is flagged Captain yet, the dropdown says so instead of showing every pending player.
3. **Fixtures** — from the Teams tab's Match Fixtures panel, **Create Fixture** (needs at least 2 teams) offers **Round Robin** (every team plays every other team once) or **Pool Play** (only enabled for more than 6 teams — enter a max teams per pool and teams are split randomly into balanced pools, round-robin within each). Either way, matches are ordered so a team doesn't play back-to-back unless every remaining match would force it (mathematically unavoidable once a group drops to 3–4 teams). The schedule shows up in its own **Fixtures** tab (next to Players/Teams), grouped by pool, alongside a **Points Table** (played/won/lost/tied/points/NRR, sorted by points then net run rate); **Regenerate Fixture** reshuffles and replaces it. When the schedule is ready, **Finalize Fixtures** (with a confirm-before-you-commit popup) locks it — after that, regenerating or deleting fixtures is blocked both in the UI and on the server, and a 🔒 Finalized badge replaces the action buttons. Clicking a match opens its detail page, showing a status chip (⏳/🔴/✅) and, once the auction is completed, each team's roster in its own tab (photo, name, category icon with a hover tooltip).
4. **Match Scoring** — once a fixture's teams have their rosters (auction completed), **Start Match** on its detail page asks who won the toss, what they chose (bat/field), and the overs per innings, then opens the live scorecard. There you pick the two opening batsmen and an opening bowler, then score ball-by-ball with a tap-to-build panel: runs (0–6), extras (Wide/No Ball, with an additional-runs picker for runs taken on that delivery — up to 6 for a No Ball, since the batter can still connect and clear the boundary running; capped at 4 for a Wide, since the bat never came into play), Bye/Leg Bye (credited as extras, never to the batter), an Over-throw toggle, and a Wicket selector (None / Out / Run Out) — **Add Ball** commits it. Rules enforced automatically:
   - Extras (Wide/No Ball) don't count as one of the over's 6 legal balls — an extra ball is bowled to replace it — and never credit the batter; the automatic 1 plus any additional runs entered all go to extras. Byes and Leg Byes, by contrast, **are** a legal ball (they count towards the over and the striker's balls-faced) — the runs just go to extras instead of the batter, since the batter didn't hit them.
   - **Run Out** — picking "Run Out" for the Wicket replaces the plain Runs picker with two questions: who was run out (**Striker** or **Non-Striker**, shown by name) and how many runs were actually completed before the dismissal (0–5). Unlike every other dismissal (which always removes the striker), a run out can take out either batter — whoever's declared out has their end vacated, and **Select the Next Batsman** now correctly fills whichever end is empty rather than assuming it's always the striker's. A run out (whether on the primary delivery or during an over-throw scramble) counts against the team's wicket tally but **not** the bowler's individual one — matching real cricket, where a run out isn't credited as one of the bowler's wickets.
   - **Over-throw** — available on a normal delivery that isn't already a boundary (any Runs value except 4 or 6), this models a fielding misthrow after the ball's already been run: pick a fixed bonus of 1–5 runs (credited as extras, same as a bye), or **Run Out** to say the extra scramble itself ended in a dismissal — which opens the same who's-out/runs-completed questions as above, scoped to just the over-throw's attempted runs.
   - Strike rotates on every run actually run — off the bat, a Wide/No Ball's extra runs, a Bye/Leg Bye, or an Over-throw — whenever that total is odd, and separately at the end of every over; both apply in sequence, so an odd-run shot on the last ball of an over nets out to no change in who's facing, exactly like real cricket.
   - A wicket clears the striker's slot (or, for a run out, whichever end was vacated) and prompts for the next batsman; an over's 6th legal ball clears the bowler and prompts for the next one (who can't be the same bowler as the over just finished).
   - **↩ Undo Last Ball** sits right on the live score card and reverts whatever the most recently recorded ball did — runs, extras, byes, an over-throw, a wicket (including a run out at either end), strike rotation, an over rollover, even a misclick that ended the innings and kicked off the chase — restoring everything to exactly how it stood before that ball, no matter which of those it triggered. It's disabled once there's nothing left to undo, and only works while the match is still live (not yet finished).
   - The first innings ends at `(squad size − 1)` wickets or once the overs run out; the second immediately ends the moment the chasing team's total reaches `first-innings runs + 1`, even mid-over.
   - **Finish Match** (only enabled once the deciding innings pair ends) locks the scorecard for good — the higher score wins 2 points, a tie splits 1 point each. **Player of the Match is calculated automatically** (runs scored + 25 × wickets taken, highest combined score across every innings played wins — a common rough fantasy-cricket equivalence, not an official formula) rather than admin-picked. Net run rate (used as tiebreaker in the Points Table) uses the full overs quota instead of actual overs faced/bowled whenever a team was bowled out, matching the standard ICC rule.
   - **Super Over** — a Semi Final or Final that finishes level shows a "Scores Level!" panel with a **Start Super Over** button instead of Finish Match (league and pool play-off matches are allowed to stay tied — only knockout matches force this). Each Super Over is a 1-over-per-side mini-match reusing the same ball-by-ball scoring UI, with one difference: only 3 batsmen are in play, so it's over after 2 wickets, even mid-over. If a Super Over also ties, another one starts automatically on request — this can repeat indefinitely, exactly like real cricket. **Batting order** alternates each time: the team that batted second in the regular match bats first in Super Over 1, and after any tied Super Over, whoever batted second in *that* one bats first in the next — so the order keeps flipping until a winner emerges. **Player rotation** kicks in from the second Super Over onward: a batter dismissed in the immediately preceding Super Over can't bat again, and whoever bowled a team's over there can't bowl it again next time (both are enforced when picking openers/a replacement batsman/a bowler, with a clear error if you try anyway). Starting a Super Over requires both rosters to have at least 3 players.
   - The consolidated scorecard (every innings played — including any Super Overs, labelled "Super Over 1 — Innings 1" etc. — with batting/bowling figures, result, Player of the Match) is always visible below the live controls, and also on the fixture's own page once the match is completed. The batting table includes each batter's **4s and 6s**.
   - **Boundaries** — a four or a six is highlighted with its own color in the "This over" ball strip (green for four, purple for six — a wicket or extra keeps its own color instead), and a 1-second animated "FOUR!"/"SIX!" overlay celebrates it the moment the ball is added. A run out's completed runs are never treated as a boundary, even when the count happens to reach 4 — that's runs via running, not a struck four.
   - **Wickets** — any dismissal (including run outs) triggers a 1-second "🎯 WICKET!" celebration overlay.
   - **Hat-tricks** — a bowler whose last two legal deliveries (wides/no-balls don't count as a ball and don't break the streak, same as the real laws) were both wickets — excluding run outs — triggers a bigger 2-second "🎩 ON A HAT-TRICK!" celebration overlay the moment they're confirmed as the bowler for the next ball, even if that ball is in a completely different over (their over in between bowled by someone else doesn't reset it, exactly like a real hat-trick can span an over they didn't bowl). Alongside it, a small pulsing "[Bowler] is on a HAT-TRICK!" badge appears right next to the live score and stays there — outlasting the celebration — until the next ball is bowled, whatever the outcome. Taking a third (non-run-out) wicket on that ball triggers an even bigger "🎩 HAT-TRICK WICKETS!" celebration overlay lasting 2.5 seconds (which takes priority over the plain wicket celebration).
   - A wicket or hat-trick celebration always plays out **on the scorecard itself first** — the score/wicket count update and the "Select the Next Batsman"/"Select the Next Bowler" prompt (or the innings-ended panel) are all held back until the celebration finishes, rather than the prompt appearing underneath or over it immediately. A plain four/six doesn't hold anything back, since neither one can trigger a next-batsman/next-bowler transition.
5. **Tournament Brackets** — created automatically alongside the league schedule, shown as **TBD**-labelled placeholder fixtures (e.g. "Rank 1 vs Rank 4") until the teams they depend on are decided:
   - **Round Robin**: 6 or fewer teams gets a single **Final** (Rank 1 vs Rank 2 from the league table); more than 6 gets **Semi Final 1** (Rank 1 vs Rank 4), **Semi Final 2** (Rank 2 vs Rank 3), and a **Final** between the two semi-final winners.
   - **Pool Play**: only when more than 4 pools are created, each pool's eventual winner is entered into a **Play-offs** round-robin among themselves (scheduled with the same back-to-back-avoiding logic as any other round robin) — which then feeds the same Semi Final/Final structure above, sized off the number of pool winners. With 4 or fewer pools, no play-off stage is added.
   - Placeholders resolve automatically the moment the stage feeding them finishes: finishing the last league (or play-off, or semi-final) match immediately fills in the real teams for whichever fixture was waiting on it. The league Points Table only ever reflects league-stage results — play-offs, semi-finals and the final don't count toward it.
   - Once the **Final** is completed, a gold banner appears at the top of the Manage Auction page announcing the tournament winner, linking straight to the Final's scorecard. The same banner also names the **Player of the Tournament** — same scoring formula as Player of the Match (runs scored + 25 × wickets taken), but aggregated across every completed match in the room regardless of stage, computed once when the Final finishes and stored on the room. It reflects overall tournament performance, not just how someone played in the Final — a player who dominated the league stage can still win it over someone who merely had the best individual Final-match performance.
6. **Statistics** — a tab showing the **Top 5 Run Scorers** and **Top 5 Wicket Takers**, aggregated across every completed match in the room (league, play-offs, and knockouts all count here, unlike the Points Table).
7. **Live Auction** — clicking Start (or Resume) opens a dedicated live-auction page that:
   - Auto-picks the next player: **captains first** (random order) until every team has one, then remaining captains are unmarked → **icon players** (random order) until every team has one, then remaining icon players are unmarked and returned to the pool → **normal players**, cycling Batsman → Bowler → All Rounder → repeat, random within each category.
   - Shows the current player with a live bid amount; tapping a team's button places a bid. The **first** bid on a player just claims them at their base value — no step-up added — since nobody's raising anyone yet; the **second** bid onward each raise the price by the room's step-up value. So a player with no competing bidders is bought at exactly their base price.
   - **Undo** reverts the last bid by one step. **Sold** assigns the player to the leading team at the current bid and deducts it from that team's purse.
   - A team's bid button is disabled once its roster is full, once it's already the leading bidder, or once bidding would exceed `purse_remaining − (remaining_required_players × current_player_base_value)` — i.e. it can never bid away the reserve it needs for the rest of its roster.
   - **Unsold** marks the current player unsold (only available when no team has bid) and sends it back into the pool — no purse or team changes. It automatically comes up for one more offer once the main pool (captains/icons/normal) is exhausted, in a dedicated **Unsold Players Round**. If it goes unsold again there, it's retired for the rest of this run so the auction can still reach "completed" rather than looping forever.
   - Once every player is sold or permanently unsold, **Finish Auction** marks the room completed and downloads a PDF with each team's roster, sold prices, and jersey details (the same report the Teams tab's **Download Auction Report** button can generate at any earlier point too, via the shared `generateAuctionPdf` util).
   - **Abort Auction** stays available in the header for as long as the auction is in progress. It performs the same reset as below (undo every sale, refund every purse, restore captain/icon designations, room back to "Created") but from mid-auction, for when a run needs to be scrapped and restarted rather than played out to completion.
8. **Trade** — a tab listing all teams; click one to see its roster with a **Trade** button per player. Trading opens a modal: pick another team, then check one or more of that team's players to receive in return (each shown with category and price) — a single player can be traded for several from the other side. **Submit Trade** asks for confirmation (Cancel/Proceed) before completing it. The swap only changes which team a player belongs to (sold prices and purses are untouched) and is rejected if it would push either team's roster past its player limit. **Captains can't be traded** — their Trade button is disabled (🔒) in the roster list, and they can't be selected as an incoming player either; both are enforced server-side too.
9. **Manage Auction → Unsold Players** — shows any players currently sitting unsold. Once the auction reaches "completed", a **Resume Auction for Unsold Players** button re-enters the Unsold Players Round for whoever's still unsold — even after clicking Finish.
10. **Reset Auction** — available on a completed room (from the Auction Rooms list, or the completion screen), or mid-auction via **Abort Auction** on the Live Auction page. Puts every player back in the pool (including restoring the original captain/icon designation for whoever got unmarked mid-auction), clears sold prices and jersey assignments, refunds every team's purse back to the room's starting purse value, and returns the room to "Created" so it can be started fresh.

## Setup

### 1. Database

Make sure MySQL is running, then create the schema:

```bash
mysql -u root -p < backend/src/db/schema.sql
```

This creates the `cricket_auction` database with `auction_rooms`, `players`, `teams`, and `bid_history` tables.

If you have an existing database from before the live-auction feature, run the migration instead (it's additive — safe to run once on an existing DB):

```bash
mysql -u root -p < backend/src/db/migrations/002_auction_engine.sql
mysql -u root -p < backend/src/db/migrations/003_reset_support.sql
mysql -u root -p < backend/src/db/migrations/004_unsold_support.sql
mysql -u root -p < backend/src/db/migrations/005_player_photo.sql
mysql -u root -p < backend/src/db/migrations/006_admin_auth.sql
mysql -u root -p < backend/src/db/migrations/007_fixtures.sql
mysql -u root -p < backend/src/db/migrations/008_fixtures_finalized.sql
mysql -u root -p < backend/src/db/migrations/009_match_scoring.sql
mysql -u root -p < backend/src/db/migrations/010_tournament_brackets.sql
```

### 2. Backend

```bash
cd backend
cp .env.example .env   # edit DB credentials, and set JWT_SECRET (see the generation command in .env.example)
npm install
npm run dev             # http://localhost:5000
```

Create an admin account (required — there's no signup page, only this script):

```bash
node scripts/seedAdmin.js <username> <password>   # password must be 8+ characters
```

Running it again with the same username updates that admin's password instead of creating a duplicate.

### 3. Frontend

```bash
cd frontend
npm install
npm run dev             # http://localhost:5173
```

The Vite dev server proxies `/api` and `/uploads` requests to `http://localhost:5000`, so no CORS setup is needed in development.

## Notes

- Hat-trick detection (`bowlerOnHatTrick` in `getMatchState`, `matchEngine.js`) is computed fresh on every fetch rather than stored as a flag anywhere — it queries the current bowler's last two `match_balls` rows with `extra_type = 'none'` in this innings and checks both were `is_wicket AND NOT is_run_out`, and only when `current_bowler_id` is actually set (no bowler confirmed yet ⇒ always `false`). Scoping the lookup to "this specific bowler's own legal deliveries" (not "the innings' last two balls") is what makes it correctly survive an over bowled by someone else in between, and re-evaluate to `false` automatically the instant a different bowler is selected. It's scoped to a single `match_innings` row, so it does not carry a streak across a Super Over boundary (a new `match_innings` row) — an intentionally out-of-scope edge case.
- The frontend (`Scorecard.jsx`) has two separate places it can notice a bowler just went on a hat-trick, because the `current_bowler_id` guard above means the transition isn't always visible right after the wicket ball itself. If the bowler's two wickets land on the last two balls of *their own* over, the bowler slot goes vacant on that very ball (no bowler confirmed yet, so `bowlerOnHatTrick` reads `false` in that response) — the transition only becomes visible once they're picked again via `handleSelectBowler` for some later over, so that handler independently checks the freshly-selected bowler's `bowlerOnHatTrick`. Otherwise (the two wickets fall mid-over, with deliveries left for the same bowler to continue), `handleAddBall` catches the transition itself by comparing the *pre-ball* `bowlerOnHatTrick` against the fresh value in the server's response to that same ball. Both paths converge on the same two effects: a 2-second "ON A HAT-TRICK!" celebration, and `onHatTrickNotice` (a local boolean, not read from the server) flipping on — which then only ever flips back off at the very start of the *next* `handleAddBall` call, regardless of what that next ball turns out to be, so the on-screen badge reliably clears "on the next ball bowled" as asked, even on an extended streak where the server's own flag would have stayed `true`.
- The 1-second plain "🎯 WICKET!" celebration is the lowest-priority ball outcome in `handleAddBall`'s if/else chain — a hat-trick-completing wicket or a fresh hat-trick transition both pre-empt it, so a single ball never stacks two celebrations.
- For a wicket-related celebration, `handleAddBall` deliberately doesn't call `setMatch` on the server's response right away — it's the `setMatch` call that flips the screen over to "Select the Next Batsman"/"Select the Next Bowler" (or the innings-ended panel), since those are all just conditions derived from the fresh match state. Applying that response (`setMatch` + `resetBallEntry` + the hat-trick badge, bundled into one `applyUpdate` closure) is deferred via `setTimeout` for exactly as long as the celebration plays (1s/2s/2.5s to match), so the prompt only appears once the celebration has actually finished on the scorecard. `ballSubmitting` is deliberately held `true` for that entire window too (only `applyUpdate` sets it back to `false`) — it already disables the Add Ball button, and now also the Undo button, closing a real race: without it, an admin could undo mid-celebration against a server that's already recorded the new ball, and the deferred `applyUpdate` would then overwrite that undo with stale data once its timer fired. A four/six never defers anything, since neither one can lead to a next-batsman/next-bowler transition.
- Fours and sixes (`match_player_stats.fours`/`sixes`) increment only when `battingRuns` is 4 or 6 on a delivery that isn't a wicket — a run out's completed-runs count is capped at 5 and credited as `battingRuns` too, so without the `!isWicket` guard a 4-run run out would wrongly register as a boundary. Extras/byes/over-throw bonus runs are never eligible in the first place since they force `battingRuns` to 0.
- The team roster modal (`.roster-modal` in `styles.css`) deliberately splits into a fixed `.modal-header` and a separately-scrolling `.modal-body`, instead of letting the whole `.modal-card` scroll like the other modals do. Putting `overflow-y: auto` and `border-radius` on the same box lets the browser's scrollbar sit flush against the rounded edge while scrolling, squaring off the top-right/bottom-right corners — only visible mid-scroll, not in a resting screenshot, which is why it's easy to miss in review. The outer card stays a plain, non-scrolling rounded frame (`overflow: hidden` just clips to that shape); the inner body is an ordinary rectangle well inside the rounded edge, so its scrollbar never touches a curve. This also means the header and the "Player / Jersey # / Size / Sleeve" column labels (`.roster-header-row`, `position: sticky`) stay visible while a long roster scrolls underneath. `.modal-body` itself carries no top padding — a sticky child's stuck offset is measured from its scroll container's *padding* edge, not the visibly clipped edge, so any top padding there would leave exactly that much of a gap at the very top of the scrollport where whatever's scrolled underneath still peeks out above the "stuck" header. The equivalent visual spacing is a `margin-top` on `.owner-editor` (the body's first child) instead, which scrolls away normally without affecting where the header locks.

- Direct captain assignment (`assignCaptain`/`unassignCaptain` in `teamController.js`) reuses the exact same `players` columns a normal auction sale writes (`team_id`, `sold_price`, `auction_status = 'sold'`, plus `is_captain`/`original_is_captain`) rather than inventing a parallel "pre-assigned" state — it's exactly as if the player had been bought in the auction, just without the bidding. That's what makes exclusion automatic: every auction-pool query already filters on `auction_status = 'pending'`, so a directly-assigned captain simply never appears, with no separate flag to keep in sync. It also means **Abort/Reset Auction** — which blanket-reverts every player back to `pending` — undoes a direct assignment exactly like it would an auction win; that's intentional, since resetting is meant to let the whole setup (captains included) be redone. `original_is_captain` is set alongside `is_captain` so a reset restores them as a captain-flagged candidate rather than a plain player.
- Match scoring (`backend/src/services/matchEngine.js`) tracks state per innings (`match_innings`), a full ball-by-ball log (`match_balls`), and per-player batting/bowling figures (`match_player_stats`, one row per player per innings, created as soon as they're selected as a batsman/bowler — not lazily on their first ball, so a not-out batsman who never faced a delivery still shows up on the scorecard). Squad size for the "all out" threshold is the count of players actually on that team's roster (`team_id = ?`), not the room's configured `num_players`. Player of the Match and Player of the Tournament share one `pickTopPerformer(rows)` helper (runs + 25 × wickets, highest wins) — the only difference is the SQL feeding it: Player of the Match aggregates `match_player_stats` for one fixture, Player of the Tournament aggregates across every `completed` fixture in the room, joined through `match_innings` regardless of `stage`.
- **Undoing a ball** (`undoLastBall` + `recomputeInnings` in `matchEngine.js`) deliberately doesn't try to invert the one ball's delta in place — a single ball can rotate the strike, roll over the bowler, or end the innings outright, and reversing each of those individually is easy to get subtly wrong. Instead it deletes the single most recent `match_balls` row anywhere in the fixture (found via `ORDER BY id DESC LIMIT 1`, not scoped to "the current innings", so repeated undo calls correctly walk backward across an innings boundary), then replays every remaining ball in that innings from scratch to rebuild its totals and every player's figures. `match_innings.opening_striker_id`/`opening_non_striker_id`/`opening_bowler_id` (set once by `selectOpeners` and never touched again) give the replay its starting point; whoever replaced an outgoing striker or bowler mid-innings is recovered with a one-ball lookahead — the very next ball's `batsman_id`/`bowler_id` always names them, since no further ball could have been recorded without that selection happening first. If the undone ball was the one that ended an odd-numbered innings and auto-created its chase half (or a Super Over that was manually started right after), that now-empty next innings is deleted too and `fixtures.current_innings` steps back down.
- **Ball scoring detail** (`parseBallDetail()` in `matchEngine.js`) normalizes a ball's raw request body into one shape — batting credit, extras total, who (if anyone) is out, and how many runs were actually run — before any database write happens, and `recomputeInnings()`'s replay derives that exact same shape from a stored `match_balls` row, so live scoring and undo-replay can never compute a ball differently. A few deliberate scope limits keep the combinations tractable: a run out only applies to a normal legal delivery (not layered onto a Wide/No Ball or Bye/Leg Bye — record it as a standard wicket instead), Over-throw only applies to a boundary-free delivery off the bat with no wicket already on it, and Byes/Leg Byes can't be recorded together with a Wide or No Ball. Over-throw runs and a run out's completed runs are always credited as extras, never to the batter — same as a bye, since both represent a fielding outcome rather than the shot itself. A run out is the one dismissal that can vacate either end: `runOutPlayer` names the actual pre-ball striker or non-striker (never a fixed role), the total runs run (off the bat/extras/byes/over-throw, whichever applied) decide whether the pair crossed, and whichever end that leaves empty is what `selectBatsman()` fills next — it writes to whichever of `striker_id`/`non_striker_id` is actually `NULL` rather than assuming it's always the striker's.
- Tournament brackets (`backend/src/services/tournamentEngine.js`) work by inserting placeholder `fixtures` rows (`team1_id`/`team2_id` left `NULL`, with human-readable `team1_placeholder`/`team2_placeholder` text like `"Rank 1"` or `"Winner SF1"`) at the same time as the league schedule, tagged with a `stage` (`league` / `pool_playoff` / `semifinal` / `final`). `maybeAdvanceTournament()` runs after every `finishMatch()` call and is a no-op unless the stage feeding the next one has just fully completed, in which case it computes standings from exactly that stage's fixtures and writes the resolved team ids onto the placeholders. A tied semifinal or final is resolved with a Super Over rather than left stuck: innings are numbered 1/2 for the main match, 3/4 for the first Super Over, 5/6 for the second, and so on — odd innings always "bat first", even innings always "chase", and `recordBall()`'s over/innings-transition logic is written generically against that parity rather than hardcoding innings 1 and 2, so the exact same code path drives the main match and every Super Over. The one behavioral difference for innings past the 2nd is the all-out threshold: a Super Over only ever has 3 nominated batsmen, so `squadSize` is hardcoded to 3 (all out after 2 wickets) instead of querying the real roster size — which is also why `startSuperOver()` separately checks both rosters have at least 3 players before allowing one to start. Batting order alternates every Super Over (`startSuperOver()` hands the new pair to whoever batted second in the most recently completed pair, main match or prior Super Over alike), and from the second Super Over onward `getSuperOverIneligiblePlayers()` blocks re-selecting a batter dismissed, or a bowler used, in the immediately preceding Super Over.
- Fixture scheduling (`backend/src/services/fixtureScheduler.js`) generates every pairing for the group (all teams for Round Robin, or each pool's teams for Pool Play), shuffles it, then greedily orders matches so consecutive ones never share a team — falling back to a repeat only when every remaining match involves a team that just played (structurally unavoidable once a group is down to 3–4 teams). Pool assignment deals teams round-robin-style into `ceil(teamCount / maxTeamsPerPool)` pools so no pool exceeds the requested max and sizes differ by at most one — a max that would leave any pool with only 1 team (no possible match, so no way to determine that pool's winner) is rejected up front.
- Passwords are hashed with bcrypt (`bcryptjs`, 10 salt rounds) before being stored — the `admins` table never holds plaintext. Sessions are JWTs signed with `JWT_SECRET` (`backend/.env`), valid for `JWT_EXPIRES_IN` (default `12h`); the frontend stores the token in `localStorage` and an axios interceptor (`frontend/src/api/client.js`) attaches it to every request and redirects to `/login` on a 401.
- Uploaded team logos are stored in `backend/uploads/logos` (2MB limit), player photos in `backend/uploads/players` (3MB limit), both served under `/uploads/<subfolder>/<filename>`. Limits are enforced both client-side (immediate feedback) and server-side (`backend/src/middleware/upload.js`).
- The PDF export runs client-side (`jspdf` + `jspdf-autotable`) — no server-side file storage involved.
- The purse-reserve rule uses the *current player's* base value as the per-slot reserve for a team's remaining roster spots — adjust `maxAllowedBid` in `frontend/src/pages/LiveAuction.jsx` and the matching check in `backend/src/controllers/auctionEngineController.js` if you rather reserve against a fixed default base value instead.
- The first-bid-at-base-price rule (`placeBid` in `auctionEngineController.js`) keys off `room.current_bid_amount == null` — that column is reset to `NULL` every time a new player comes up (`pickNextPlayer`) and by `undoBid` once the last bid on the current player is undone, so both "a brand new player" and "undid every bid back to zero" correctly fall back to base price on the next bid rather than base + step-up. The frontend mirrors the exact same check (`nextBidAmount` in `LiveAuction.jsx`) so a bid button's tooltip and its afford-ability gating both show the true amount a click would place, not an inflated one.
- Known limitation: if the total players in the pool exceed the combined roster capacity of all teams (`sum of team.num_players`), the auction can never reach "completed" — the last unsellable players have no team left with a free slot to buy them. Make sure total roster capacity ≥ total player count before starting.
